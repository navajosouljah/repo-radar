Knowledge that remembers time

Utopia is a knowledge graph that tracks not just what is true, but when it was true and when you learned it. Combined with GraphRAG and semantic search, it gives enterprises a structured memory layer that LLMs can reason over.

● Core capabilities

Bitemporal knowledge tracking

Every fact in the graph carries two timestamps: valid time (when the fact was true in the real world) and transaction time (when it was recorded in the system). This means you can query what you knew at any point in time - and what was actually true at any point in time.

GraphRAG retrieval

Instead of naive vector similarity, Utopia walks the knowledge graph to find context-relevant facts before passing them to an LLM. The graph structure provides relationship-aware retrieval that flat embedding search cannot match.

Ontology-first schema design

You define entity types, relationship types, and constraints in an ontology before ingesting data. This is not a property graph where anything goes - the schema enforces structure, making queries predictable and the graph navigable.

PostgreSQL + pgvector backend

Utopia stores the graph in PostgreSQL with pgvector for embeddings. No exotic database to manage - your existing Postgres infrastructure, backup tooling, and operational knowledge all apply.

Pure Rust performance

The core engine is written in Rust, delivering the memory safety and performance characteristics you would expect. Graph traversals, temporal queries, and embedding lookups all benefit from Rust's zero-cost abstractions.

Semantic search

Beyond graph traversal, Utopia supports vector similarity search over entity descriptions and relationships. Combine structured graph queries with fuzzy semantic matching for the best of both retrieval paradigms.

Key differentiator

Bitemporality makes knowledge graphs trustworthy

Most knowledge graphs store only the current state of the world. Utopia tracks when facts became known and when they were true, separately. This means you can answer "What did we believe about this customer on March 15?" and "When did we first learn this regulation changed?" - questions that are critical for compliance, auditing, and debugging AI decisions. It is the difference between a snapshot and a time machine.

The knowledge problem

Enterprise knowledge is scattered across documents, databases, wikis, and people's heads. It changes constantly, and nobody tracks when or why it changed.

Today's reality

Knowledge lives everywhere. Customer data in the CRM, policies in the wiki, decisions in email threads, context in people's heads. There is no unified graph connecting these entities. When someone leaves, their knowledge walks out the door.

No temporal context. Traditional databases store the current state. When a regulation changes or a customer's status updates, the previous state is overwritten. You cannot answer "What did we know when we made that decision?" - a question auditors and regulators ask constantly.

RAG without structure hallucinates. Flat vector search retrieves text chunks by similarity, but it has no concept of entity relationships, time, or validity. An LLM fed context from naive RAG may confidently cite outdated information or conflate two unrelated entities that happen to share similar descriptions.

With Utopia

One graph, all knowledge. Entities - people, policies, products, regulations - live in a single knowledge graph with typed relationships. The ontology enforces consistent structure, making the graph queryable and navigable rather than a dump of unstructured triples.

Full temporal audit trail. Every fact records when it was true (valid time) and when the system learned it (transaction time). You can reconstruct the state of knowledge at any historical moment - for compliance, debugging, or simply understanding how things evolved.

Graph-aware retrieval. GraphRAG traverses relationships to find relevant context, not just similar text. When you ask about a customer, it follows edges to their contracts, their industry's regulations, and the team that manages them - structured context an LLM can reason over reliably.

● Key concepts

Valid Time

When a fact was true in the real world. A customer's address changed on June 1 - that is the valid time. Even if the database was not updated until June 15, the fact was valid from June 1.

Transaction Time

When the system recorded the fact. The address update was entered on June 15 - that is the transaction time. This lets you answer "What did the system believe on June 10?" (the old address, because the update had not been entered yet).

Ontology

The schema for your knowledge graph. You define entity types (Person, Policy, Product), relationship types (manages, governs, contains), and constraints before ingesting data. The ontology prevents garbage from entering the graph.

GraphRAG

Graph-structured retrieval for LLMs. Instead of retrieving text chunks by vector similarity alone, GraphRAG walks the knowledge graph's edges to gather relationship-aware context. The result is more precise, more complete, and less likely to mislead the model.

Get started

Install the CLI, connect to PostgreSQL, define your ontology, and run your first GraphRAG query. Requires a running PostgreSQL instance with pgvector enabled.

1

Install the Utopia CLI

# Install from crates.io
cargo install utopia-cli

# Or build from source
git clone https://github.com/deeplethe/utopia.git
cd utopia
cargo build --release

Requires Rust 1.75+ and a running PostgreSQL 15+ instance with the pgvector extension installed.

2

Initialize the database

# Point Utopia at your PostgreSQL instance
utopia init --pg-url postgres://user:pass@localhost:5432/utopia_db

# This creates the schema, enables pgvector,
# and sets up bitemporal tracking tables

The init command creates all required tables, indexes, and the pgvector extension. It is idempotent - running it twice will not corrupt existing data.

3

Define your ontology

# ontology.yaml
entities:
  - name: Person
    properties:
      - { name: full_name, type: string, required: true }
      - { name: role, type: string }
      - { name: department, type: string }

  - name: Policy
    properties:
      - { name: title, type: string, required: true }
      - { name: effective_date, type: date }
      - { name: status, type: enum, values: [draft, active, retired] }

relationships:
  - { name: manages, from: Person, to: Person }
  - { name: authored, from: Person, to: Policy }
  - { name: supersedes, from: Policy, to: Policy }

# Apply the ontology
utopia ontology apply ontology.yaml

The ontology is versioned. Changing it creates a new version, and the graph tracks which ontology version each fact was ingested under. You can evolve the schema over time without breaking existing data.

4

Ingest knowledge

# Ingest entities and relationships from JSON
utopia ingest entities.json

# Or use the Rust API directly
use utopia::{Client, Entity, Relationship};

let client = Client::connect("postgres://...").await?;

client.upsert_entity(Entity {
    entity_type: "Person",
    properties: json!({
        "full_name": "Alice Chen",
        "role": "VP Engineering",
    }),
    valid_from: "2025-03-01".parse()?,
}).await?;

Every ingested fact automatically receives both valid time (from the data) and transaction time (the moment of ingestion). Embeddings are generated for semantic search on ingest.

5

Query with GraphRAG

# Natural language query via CLI
utopia query "Who manages the compliance team and what policies did they author?"

# Temporal query - what did we know on a specific date?
utopia query "What was the active data retention policy?" \
  --as-of-valid "2025-06-15" \
  --as-of-transaction "2025-07-01"

# The GraphRAG engine:
# 1. Embeds the question
# 2. Finds seed entities via semantic search
# 3. Walks the graph to gather relational context
# 4. Returns structured context for LLM consumption

The --as-of-valid flag filters by when facts were true. The --as-of-transaction flag filters by when the system knew about them. Combine both for full bitemporal queries.

Real-world applications

Where a bitemporal knowledge graph with GraphRAG solves problems that flat databases and naive vector search cannot.

Enterprise Knowledge

Unified organizational memory. Companies use Utopia to consolidate knowledge scattered across wikis, CRMs, and documents into a single graph. The ontology enforces consistency, and bitemporality means nothing is ever truly lost - you can always reconstruct what was known when.

Regulatory Compliance

Temporal audit trails. Financial and healthcare organizations need to prove what they knew and when. Utopia's bitemporal tracking provides a complete audit trail: "On June 15, we believed Policy X was active because it was recorded on May 1 with a valid-from date of April 15." Regulators can trace every decision.

Research Tracking

Literature and finding evolution. Research teams use Utopia to track how findings evolve over time. A paper published in March may be superseded by new results in August. The graph preserves both states and their temporal context, so you can trace how understanding shifted.

AI Agent Memory

Structured long-term memory for agents. AI agents need more than a vector store - they need structured, temporal knowledge about the world they operate in. Utopia serves as a memory layer that agents can query with --as-of semantics, avoiding the hallucination that comes from flat retrieval over stale embeddings.

In the Wild

  • Emerging concept, early traction. The "world model" framing for enterprise knowledge graphs is gaining momentum in technical discussions. Utopia is one of the first open-source projects to combine bitemporal tracking with GraphRAG under this umbrella. The 6.8K stars in just over a month suggest strong early interest, though community adoption is still in its earliest stages.
  • GraphRAG momentum. Microsoft's research on GraphRAG in 2024 popularized the idea of graph-structured retrieval for LLMs. Utopia builds on this concept by adding bitemporality and ontology management - features the original research did not address but that enterprises need.
  • Bitemporal databases are proven. The bitemporal data model is not new - it has been used in financial systems for decades. What is new is combining it with a knowledge graph and semantic search in a developer-friendly open-source package. The SQL:2011 standard included temporal support, but few databases implemented it well.
  • Honest assessment. Evidence of production deployments at scale is thin at this stage. The repo is barely a month old (created August 7, 2026), and while the architecture is ambitious, it is worth watching whether the project can deliver on the scope its "world model" framing implies. Early community engagement on GitHub issues suggests active development.

Watch out for

  • Complex ontology setup. Defining a good ontology requires domain expertise and upfront design work. Unlike a property graph where you can throw in untyped data, Utopia's ontology-first approach demands you think about entity types, relationships, and constraints before ingesting anything. This is a feature for data quality but a barrier to quick experiments.
  • PostgreSQL dependency. Utopia requires PostgreSQL with pgvector. Teams running MySQL, MongoDB, or other databases will need to add a Postgres instance. The upside is that Postgres is well-understood operationally; the downside is another database to manage.
  • Rust ecosystem barrier. Building from source requires a Rust toolchain. For teams without Rust experience, the installation and any contribution work may feel unfamiliar. Pre-built binaries and container images would lower this barrier if they become available.
  • "World model" is an ambitious claim. The term "world model" carries expectations from AI research that go beyond what a knowledge graph provides. Utopia is, at its core, a bitemporal knowledge graph with good retrieval features. Calling it a "world model" sets expectations that may overshoot what the software currently delivers. Evaluate it on its concrete capabilities, not the branding.
  • Very new project. Created August 7, 2026 - just over one month old as of this edition. The API surface, ontology format, and query interface may all change significantly. The project has strong architectural ideas but limited battle-testing. Pin versions and expect breaking changes.
