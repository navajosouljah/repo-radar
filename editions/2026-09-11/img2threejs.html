● What makes it different

Code output, not mesh files

Unlike NeRF or photogrammetry tools that produce .obj or .glb mesh files, img2threejs generates readable JavaScript code that uses Three.js primitives - BoxGeometry, SphereGeometry, ExtrudeGeometry, and CSG operations. The output is version-controllable, editable, and human-readable.

Quality gates that enforce standards

The pipeline includes configurable quality gates that evaluate the generated model against the reference image. If the output does not meet the similarity threshold, the pipeline retries with adjusted parameters. You set the bar - the system meets it or tells you why it could not.

Animation-ready from the start

Generated models are structured for animation. Each logical component is a named, separate Three.js group - wheels, body, windows for a car; legs, seat, back for a chair. This makes it trivial to add rotation, movement, or physics after generation.

Token-efficient for agent workflows

The pipeline is designed to work within LLM context windows. Generated Three.js code is compact and procedural - no base64-encoded textures, no inlined vertex arrays, no bloated JSON scenes. A typical output is 200-800 lines of clean JavaScript, well within agent token budgets.

AI-powered image analysis

The system uses vision models to decompose the reference image into geometric primitives, materials, and spatial relationships. It understands that a chair has four legs, a cylinder is a mug handle, and a sphere sits on top of a cone to make an ice cream. This semantic understanding drives the code generation.

Claude Code and agent integration

img2threejs ships with first-class support for AI agent workflows. It can be invoked as a tool call from Claude Code, Cursor, or any agent that can execute Python. The output is designed to drop directly into a Three.js project with zero manual edits.

Single best feature

Code you can read, not meshes you cannot

The fundamental insight of img2threejs is that for many use cases, a procedural Three.js code file is more valuable than a high-polygon mesh. Code can be version-controlled with git. Code can be reviewed in a pull request. Code can be modified by an LLM agent. Code can be animated by adding a few lines. Code has zero loading overhead beyond the Three.js runtime. A .glb file gives you none of those properties. For rapid prototyping, e-commerce previews, and agent-driven 3D, code-first beats mesh-first.

The 3D modeling bottleneck

Three.js makes 3D rendering accessible in the browser. But creating the 3D content itself remains a manual, expensive process that sits outside most developers' skill sets. The modeling step is the bottleneck.

Before

Manual modeling is expensive. Creating a 3D model in Blender, Maya, or Cinema 4D takes hours of skilled work. A simple product model might cost $200-500 from a freelancer. For a startup that needs 3D previews of 50 products, that is $10K-25K before writing a line of rendering code.

Existing image-to-3D creates meshes, not code. Tools like NeRF, Gaussian Splatting, and point-cloud reconstruction produce mesh files - .obj, .glb, .ply. These are opaque binary blobs. You cannot read them, diff them, or modify them programmatically. They also tend to be large and slow to load on the web.

Three.js models are hand-coded. Developers who want procedural 3D - models built from code rather than mesh files - write Three.js geometry by hand. This requires visualizing 3D coordinates in your head, placing primitives manually, and iterating through dozens of refresh cycles. It is tedious even for experienced developers.

No quality feedback loop. When an AI generates a 3D model, how do you know it is any good? Existing pipelines dump output and hope for the best. There is no automated check that the generated model actually looks like the input image. Bad outputs waste compute and developer time.

After

Image in, code out. Hand img2threejs a photograph and it returns clean, procedural Three.js JavaScript. No modeling software, no mesh files, no manual coordinate wrangling. The generated code uses standard Three.js primitives that any web developer can read and modify.

Version-controllable 3D. Because the output is code, it lives in your git repo alongside the rest of your application. Pull requests can include 3D model changes with meaningful diffs. Code review catches issues. CI can validate the output. This is how software teams already work - img2threejs makes 3D fit that workflow.

Quality gates close the loop. The pipeline compares the generated model to the reference image and scores the similarity. If the score falls below your configured threshold, it retries with adjusted decomposition. You get a guaranteed minimum quality or a clear failure - no silent bad outputs.

Agent-native by design. The pipeline's token-efficient output is explicitly designed for LLM agent workflows. An agent can generate a model, check the quality score, modify the code, and re-render - all within a single context window. This makes 3D content creation automatable for the first time.

Get generating

From installation to your first generated Three.js model in under five minutes. You will need Python 3.9 or later and access to a vision-capable LLM API.

1

Install img2threejs via pip

# Install from PyPI
pip install img2threejs

# Or install from source for the latest
git clone https://github.com/img2threejs/img2threejs.git
cd img2threejs
pip install -e .

The package installs with minimal dependencies. The core pipeline requires Python 3.9+ and handles vision model API calls, geometric decomposition, and Three.js code generation. No GPU required on your machine - the heavy lifting happens in the vision model API.

2

Configure your vision model and quality thresholds

# Set your API key for the vision model
export ANTHROPIC_API_KEY="your-key-here"

# Or configure via the settings file
img2threejs init
# Creates ~/.img2threejs/config.yaml with defaults:
#   model: claude-sonnet        (vision model)
#   quality_threshold: 0.75     (0.0 to 1.0)
#   max_retries: 3              (retry on quality fail)
#   animation_ready: true       (named component groups)
#   output_format: esm          (ES module or IIFE)

The quality threshold is the key setting. At 0.75, the pipeline accepts models that are recognizably similar to the reference. Raise it to 0.9 for higher fidelity at the cost of more retries. Lower it to 0.5 for fast, rough prototypes.

3

Generate your first Three.js model

# Generate from a reference image
img2threejs generate photo.jpg -o model.js

# Python API
from img2threejs import generate

code = generate("photo.jpg", quality_threshold=0.8)
with open("model.js", "w") as f:
    f.write(code)

# The output is a self-contained Three.js ES module
# Import it directly into your scene:
#   import { createModel } from './model.js'
#   const group = createModel()
#   scene.add(group)

The generated file exports a createModel() function that returns a Three.js Group. Each logical component - body, wheels, handle, lid - is a named child group you can target for animation, color changes, or visibility toggling.

4

Preview and iterate

# Launch the built-in preview server
img2threejs preview model.js

# Opens a browser window with:
#   - Orbit controls (drag to rotate)
#   - Reference image overlay for comparison
#   - Component tree inspector
#   - Quality score readout

# Regenerate with higher quality if needed
img2threejs generate photo.jpg -o model.js --threshold 0.9 --retries 5

The preview server renders the generated model side-by-side with the reference image. Use the component inspector to see the named groups, and edit the generated code directly - changes hot-reload in the preview.

Where it renders

img2threejs fills a gap between manual 3D modeling and mesh-based generation. Here are the workflows where procedural, code-only 3D output changes the equation.

Rapid Prototyping

Sketch to 3D in seconds, not hours. Designers and product teams photograph a whiteboard sketch, a clay model, or an existing product and generate a Three.js preview in under a minute. The output is rough but manipulable - rotate it, show it in context, share a link. For early-stage product exploration, this speed advantage is transformative. A team that previously waited days for a 3D artist can now iterate on spatial ideas within a single meeting.

E-Commerce Previews

Product photos become interactive 3D views. Online retailers with thousands of SKUs cannot afford to manually model every product. img2threejs can batch-process product photography into Three.js models that power 360-degree interactive viewers on product pages. The procedural code output keeps file sizes small - typically under 10KB per model - so page load times stay fast. Animation-ready output means you can add spin, explode, or hover effects without touching the model code.

Game Dev Pipeline

Reference art to placeholder assets, automated. Game developers use reference images - concept art, mood boards, photographs - to communicate what an asset should look like. img2threejs converts those references directly into usable placeholder 3D assets that occupy the right space, have the right proportions, and can be dropped into a scene while the real assets are being built. The animation-ready grouping means placeholders can be rigged for basic movement immediately.

Educational Content

3D models from textbook illustrations. Educators creating interactive learning materials can photograph diagrams - a human heart, a building cross-section, a molecular structure - and generate rotatable 3D models for web-based courseware. Because the output is standard Three.js code, it integrates with any web-based learning platform. Students can inspect the code itself to learn how 3D graphics work, turning the tool into both a content creator and a teaching aid.

Watch out for

  • Complex scenes may need manual refinement. The pipeline excels at single objects with clear geometry - products, furniture, vehicles, simple characters. Multi-object scenes, organic shapes with fine detail, and objects with complex internal structure will often require manual editing of the generated code. The output is a starting point, not a final asset, for anything beyond moderate complexity.
  • Quality gates can reject valid outputs. The quality comparison between generated model and reference image uses perceptual similarity metrics. Stylized or abstract references - concept art, sketches with loose lines - may score poorly even when the 3D model is a reasonable interpretation. You may need to lower the threshold or disable quality gating for non-photographic inputs.
  • Python dependency for JavaScript output. The irony is real: you need a Python environment to generate JavaScript code. For teams that are purely JavaScript/Node.js, adding Python to the toolchain is a friction point. A Node.js port is on the roadmap but not yet available. For now, the workaround is running img2threejs in a Docker container or CI pipeline.
  • Vision model API costs. Each generation requires one or more calls to a vision-capable LLM. With retries on quality gate failures, a single model might require 3-5 API calls. At current vision model pricing, that is roughly $0.02-0.10 per generated model. Batch-processing hundreds of product images will accumulate meaningful API costs.
  • Young project, evolving API. Created July 15, 2026 - less than two months old. The Python API and CLI flags may change between minor versions. The quality gate scoring is under active calibration. Pin your version with pip install img2threejs==X.Y.Z and test before upgrading in production pipelines.
