JustVugg /colibri

A pure-C inference engine that turns your GPU VRAM, system RAM, and NVMe SSD into one layered cache - so a 744B-parameter frontier MoE model runs on a laptop with 25 GB of RAM. Slow at the floor, but mathematically exact.

The hummingbird ration

MoE models only fire ~5% of their weights per token. Colibri (Italian for hummingbird) is built entirely around exploiting that gap - keep the sliver you need this instant in RAM, stream the rest off disk.

AI memory multitiering

VRAM, RAM, and NVMe become one cache ladder. Dense attention layers (~17B params, under 10 GB at INT4) stay resident; 19,456 routed experts park on SSD and stream on demand. Insufficient fast memory only changes speed, never model semantics or precision.

Dual-SSD bandwidth striping

Mirror the model to a second drive and experts stream from both at once, hash-weighted by measured bandwidth. A 9 GB/s + 3 GB/s pair reads roughly 33% faster than the fast drive alone.

I/O latency hiding

Each expert's three matrices sit adjacent on disk for a single pread. An async I/O pool (PIPE=1) loads missing experts while resident ones compute, and a router-lookahead thread (PILOT=1) prefetches the next layer's experts.

Warm restarts via compressed KV

MLA stores 576 floats per token instead of 32,768, and the compressed state persists to disk (.coli_kv) - conversations reopen warm across restarts with zero re-prefill.

Heterogeneous backends

GPU-resident CUDA pipeline (COLI_CUDA_PIPE=2), an experimental Apple Metal backend using a newBufferWithBytesNoCopy residency trick, a Vulkan 1.2 backend that revives older AMD cards dropped by ROCm, and COLI_NUMA=1 interleaving on multi-socket hosts.

One developer, then a movement

Created by Vincenzo Fornaro and tested on a plain 12-core laptop. The forward pass is validated token-exact against a reference transformer - the streaming, quantized version produces the same outputs.

Single best feature

The learning cache - it gets faster the more you use it

Colibri records which experts your prompts actually route to in a local .coli_usage file, updated every turn. At startup it automatically pins the hottest experts into spare RAM. Use it for one kind of task and the engine literally tunes its own cache for that task.

The problem it solves

Frontier-class open models exist. The hardware to hold them mostly does not - unless you stop trying to hold them at all.

Before
  • GLM-5.2 at full precision is ~1.4 TB of raw numbers. Even compressed hard, it is still 239 GB to 370 GB - pure data center territory.
  • Your options: a multi-GPU rig, a ~$15,000 maxed-out unified-memory Mac Studio, or pay-per-token cloud APIs with rate limits, privacy trade-offs, and vendor deprecation risk.
  • Even Ollama, the friendly one-click tool, refuses to load these weights locally and hands you off to a cloud endpoint instead.
After
  • The dense core every token needs (~17B params, under 10 GB at INT4) stays resident in RAM the whole time.
  • The 19,456 routed experts stay parked on a fast NVMe SSD and stream in on demand - only the handful the router calls for each token.
  • A 744B-parameter model boots in about 30 seconds holding just 9.9 GB resident, on the laptop a lot of people already have in a drawer. Colibri runs exactly where the official path gives up.

The framing shift: the model does not need to fit in fast memory - it needs to be placed across a hierarchy. RAM holds the working set, never the whole model.

Setup

The runtime is pure C with zero dependencies. Python 3 is only used by the one-time converter and the optional API gateway.

1

Install a prebuilt release

mkdir colibri && tar xzf colibri-v1.1.0-linux-x86_64.tar.gz -C colibri && cd colibri
python3 coli info   # verifies engine readiness

Or build from source (needs gcc or clang with OpenMP):

git clone https://github.com/JustVugg/colibri && cd colibri/c
./setup.sh          # checks compilers, builds, runs self-tests

Run pip install -e . from your checkout to put the coli command on your PATH.

2

Download the model (~372 GB)

Grab the pre-converted GLM-5.2 INT4 group-scaled (gs64) container with the INT8 MTP head from Hugging Face:

https://huggingface.co/mastouri/GLM-5.2-colibri-int4-g64-with-int8-mtp

Or convert FP8 weights yourself:

./coli convert --model /nvme/glm52_i4
3

Preflight and tune

COLI_MODEL=/nvme/glm52_i4 ./coli plan     # inspect planned VRAM/RAM/disk placement
COLI_MODEL=/nvme/glm52_i4 ./coli doctor   # standard preflight check
COLI_MODEL=/nvme/glm52_i4 ./coli doctor --deep  # strict tensor/shard preflight
COLI_MODEL=/nvme/glm52_i4 ./coli tune     # measures and saves fastest profile
4

Run it

COLI_MODEL=/nvme/glm52_i4 ./coli chat     # TUI chat (Windows: python coli chat --model D:\glm52_i4)
./coli web --model /nvme/glm52_i4         # API gateway + web dashboard, auto-opens browser
./coli serve --model /nvme/glm52_i4       # headless API gateway
5

Optional: dual-SSD striping

COLI_MODEL=/fast/glm52_i4 COLI_MODEL_MIRROR=/second/glm52_i4 ./coli chat

Stage a partial mirror to a smaller secondary drive:

./c/coli mirror plan  --model /fast/glm52_i4 --mirror /second/glm52_i4 --budget-gib 200 --reserve-gib 20
./c/coli mirror stage --model /fast/glm52_i4 --mirror /second/glm52_i4 --budget-gib 200 --reserve-gib 20
./c/coli mirror verify --model /fast/glm52_i4 --mirror /second/glm52_i4

Real-world numbers

Same engine, same 744B model, wildly different speeds. The lesson across every benchmark: RAM volume and disk bandwidth drive local MoE performance, not GPU compute.

5.8 - 6.8 tok/s

6x RTX 5090 rig, full residency

The top of the published range, with time-to-first-token around 13 seconds. The fastest configs are still serious machines.

No GPU, still wins

High-RAM dual-Xeon server (1 TB RAM)

Beats a single RTX 5090 workstation "by a mile" because the entire expert set stays resident in memory. It all comes back to the memory.

~1.8 tok/s

128 GB CPU-only desktop

Respectable decode speed once the learning cache is warm - no graphics card involved. An RTX 5070 Ti laptop-class box lands at 1.07 tok/s via the GPU-resident pipeline.

0.1 tok/s

MacBook M2 Max, 32 GB, external USB SSD (1 GB/s)

Over 2 minutes to first token. Profiling showed 145 of 158 seconds - over 80% of the turn - was pure disk waiting; actual math took 7 seconds. The chip was never the problem.

8x faster

Same model, better placement

Moving to a workstation with an RTX 5090, 64 GB RAM, and a fast internal SSD lifted the same workload to 0.8 tok/s, cut TTFT to 17 seconds, and halved disk waiting to 48%. The upgrade that mattered was double the RAM and the internal drive, not the GPU.

0.05 - 0.1 tok/s

The 25 GB laptop floor

Roughly one word every 10 seconds cold - each word requires physically reading about 11 GB of expert data. Painfully slow, but with perfect mathematical correctness. The use case is queueing deep tasks overnight, not conversation.

Watchouts

The project is honest about its trade-offs, and the community has mapped the sharp edges. Know these before you clear 400 GB of disk.

SLOW STORAGE = SLOW EVERYTHING

Without a fast internal NVMe drive the engine is painfully slow - practical for queueing deep tasks overnight, not active chat. The whole trick is constantly streaming model pieces off disk, so the disk sets the ceiling.

MASSIVE DISK REQUIREMENTS

GLM-5.2 is 372 GB, Inkling is 469 GB, DeepSeek V4 Flash is 167 GB, and Kimi K3 is 1.6 TB. Freeing that much internal SSD space is a real barrier on standard laptops - it is the first wall most users hit, before RAM or GPU even comes up.

OLD QUANTIZATIONS DEGRADE HARD

Older per-row INT4 mirrors (the mateogrgic/... and jlnsrk/... uploads) cause a ~9 percentage point quality drop plus endless repeating-text and think-mode loops. Use the newer group-scaled (gs64) build, full stop.

MTP HEAD MUST BE INT8

If the Multi-Token Prediction head is quantized to INT4, draft token acceptance collapses to 0% - 4% and speculation is useless. The reference container ships the INT8 MTP head for a reason.

DEEPSEEK V4 SPECULATIVE DRAFTING IS OFF BY DEFAULT

On the DeepSeek V4 Flash engine, V4_DRAFT and V4_MTP default to 0: measured on real multi-turn chat, the rejected-suffix replay of the recurrent attention state cost more than the drafts saved - one 14-token answer took 495 seconds. The code stays in the tree, with the numbers beside it, for anyone retrying on faster storage.

DIRECT=1 IS DRIVE-DEPENDENT

O_DIRECT bypassing the page cache is often a large win on drives with DRAM cache and bandwidth headroom, but on QLC, DRAM-less, or virtualized drives it can be neutral to negative. Try it first; keep what your hardware rewards.
