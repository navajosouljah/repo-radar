★ Single best feature

On-demand expert streaming under a rolling memory budget

Memory is treated as a strict accounting budget, not a container to fill. An 8-bit router evaluates the current token, pulls exactly eight specific experts off the SSD in real time, and computes the active layers on the GPU while the other 120 experts stay asleep on the drive. A 16-slot LFU cache per layer exploits the roughly 40% expert overlap between neighboring tokens so the same weights are not re-read from disk.

Parallel pread instead of mmap

Rather than blocking on memory mapping, the CPU coordinates router expert IDs against cache misses and issues bounded, parallel pread calls straight into Metal-visible buffers.

Streaming repack installer

TurboFieldfareRepack pulls the Hugging Face checkpoint via range requests and writes it straight into a custom .gturbo layout - no raw shard files staged on disk.

Loopback OpenAI-compatible server

Bundled local server with Chat Completions, streaming, single-prefix prompt reuse to bypass prefill costs, and function-tool call support.

Dual KV cache storage

Exact split-K/V decode attention: circular storage for the 25 sliding-window layers, linear storage for the 5 full-attention layers.

The memory wall

Big MoE models do not need all their weights at once - but every mainstream local runtime loads them as if they do.

Before · load everything
  • Gemma 4 26B is roughly 14.3 GB of weights at compressed 4-bit precision.
  • Under Apple's MLX or llama.cpp, all 14.3 GB must be resident in RAM - physically impossible on a base 8 GB MacBook Air.
  • The workarounds: unified-memory workstations from $7,000 and up, or renting cloud GPUs by the hour, forever.
After · stream the experts
  • Memory becomes a rolling accounting budget, not a container to fill all at once.
  • Only the 1.35 GB shared core and the FP16 KV cache live permanently in RAM.
  • Idle routed experts park on the SSD and stream on demand per token - active footprint drops to about 2 GB.
  • Result: a 26B model running on the cheapest 8 GB M-series Mac Apple sells, for $0 in cloud fees.
Why it matters

A 26B model does not have to live in someone else's data center

The thesis was proven publicly, fast: from a private repo to a Hacker News front page in 12 days, by one engineer. One path costs $7,000 and up in hardware or an endless cloud meter; the other is a git clone on a Mac you may already own. Not the same job - but only one of them is free.

Get it running

Three commands, no account, no sign-in wall. The pinned model download is a one-time ~15 GB network transfer.

Requirements: Apple Silicon Mac, macOS 26 with Metal 4, Xcode 26, Swift 6.2 or newer, and roughly 14.3 GB of free storage.

1Clone and build from source

git clone https://github.com/drumih/turbo-fieldfare.git
cd turbo-fieldfare
swift build -c release
.build/release/TurboFieldfareMac

On first run, Swift Package Manager automatically downloads the required tokenizer packages.

2Download the model (GUI or CLI)

GUI: in the native Mac app, choose Download to stream and repack the pinned model (about 15 GB transfer), then Load Model and start prompting.

CLI:

swift run -c release TurboFieldfareRepack --output scratch/gemma4.gturbo --overwrite
# resume an interrupted download:
swift run -c release TurboFieldfareRepack --output scratch/gemma4.gturbo --overwrite --resume
# verify a completed install manifest:
swift run -c release TurboFieldfareRepack --verify-install --input-gturbo scratch/gemma4.gturbo

3Chat from the terminal

Create a local messages.json:

[
  {"role": "user", "content": "Explain why chunked prefill reduces time to first token while keeping memory bounded."}
]

Then run the CLI chat:

swift run -c release TurboFieldfareCLI --model scratch/gemma4.gturbo --messages-file messages.json

4Run the local OpenAI-compatible server

swift build -c release --product TurboFieldfareServer
.build/release/TurboFieldfareServer --model scratch/gemma4.gturbo

The server listens on http://127.0.0.1:8080/v1 and supports tool calls.

On the dyno

Community-measured numbers, including honest comparisons against the frameworks it undercuts on memory.

5.1-6.3tok/s · 8 GB M2 Air

The headline unlock

On the cheapest M2 MacBook Air Apple sells, the 26B model generates a respectable 5.1 to 6.3 tokens per second under the strict 2 GB memory ceiling - hardware that previously could not run this model at all.

31-35tok/s · 24 GB M5 Pro

Scales with the chip, not the budget

On a 24 GB M5 Pro the same trick hits 31 to 35 tokens per second (some tests report 24 to 35) at the exact same 2 GB allocation. The memory math never changes; only the streaming gets faster.

8xmmap → pread

The unglamorous fix that made it work

Early experiments with standard mmap yielded 0.5 tok/s with a 10 ms cold-expert load. Switching to optimized parallel pread calls cut expert loads to 2.8 ms and lifted throughput to 4 tok/s - an 8x improvement from a smarter read pattern, not an architecture change.

75 vs 35tok/s · MLX vs TF

The honest trade against MLX

Apple's own MLX runs the same model at 75 tokens per second on an M5 Pro - more than double TurboFieldfare's speed - but consumes 14 GB of memory to do it. More speed for seven times the RAM: that is the real trade behind the headline.

6-10tok/s · llama.cpp CPU

And against llama.cpp

Running the model CPU-only (GPU layers set to zero) in llama.cpp on 16 GB Macs yields 6 to 10 tokens per second - which outperforms the 8 GB Air unlock, if you have the RAM to spare.

Read the warning label

A clever proof of concept, not a production system - and the tradeoffs are physical, not just theoretical.

⚠ Watch out for

  • SSD wear and battery drain. Constant expert streaming triggers physical disk reads on every token. A 2026 arXiv study ("SSD Offloading for LLM Mixture of Experts Weights Considered Harmful in Energy Efficiency") finds this can multiply per-token energy consumption by close to an order of magnitude - heavy battery drain plus accelerated drive wear.
  • The model itself is weak at code. The engine runs Gemma 4 fine, but in an independent test the model scored 33.33% on a standard coding suite and failed all 21 test cases. Not a coding-agent replacement, and the creator never claimed it was.
  • Slow drives kill it. On an external USB SSD transferring at 1 GB/s, community tests saw disk waits eat over 80% of run time (145 of 158 seconds), generation crash to 0.1 tok/s, and time to first token blow past 2 minutes.
  • One model, period. TurboFieldfare is not a general runtime - it runs exclusively Google's instruction-tuned Gemma 4 26B-A4B. The trick also fails entirely on dense models, which keep every parameter active per token.
  • Context window RAM bleed. Gemma 4 supports up to a 256K token context, but the KV cache must stay resident in unified memory - long conversations steadily consume the tiny allocation that makes the 2 GB limit possible.
  • Sequential and text-only. Generation is a single-file sequential decode loop with no batching, and there is no image, audio, or video input support.
