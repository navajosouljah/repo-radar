DeepSeek V4 Flash, GLM 5.2, and DeepSeek V4 PRO on high-end personal machines, with its own CUDA and Metal backends, disk-persistent KV cache, and a native coding agent.

Radical specialization

Where generic runners chase every GGUF on Hugging Face, DwarfStar bundles model loading, prompt rendering, tool calling, KV state management, an HTTP server that speaks OpenAI, Anthropic, and Responses APIs, and an in-process coding agent - all tuned for exactly three heavyweight models.

Asymmetric expert quantization

Instead of a naive full-model quant that destroys accuracy, only the routed MoE experts get compressed to 2-bit (IQ2_XXS up/gate, Q2_K down tensors). Dense attention projections, shared experts, and routing layers keep higher precision.

Dual KV cache with disk spill

The active session lives in RAM; switching sessions or restarting the server flushes KV state to SSD as a <sha1>.kv file. Prompts matching a cached prefix skip prefill and load token IDs and graph state straight from disk.

SSD streaming mode

When VRAM and RAM cannot hold the whole model, non-routed weights and activations stay resident while heavy MoE experts park on disk and stream in on cache misses.

RDMA tensor parallelism

Two Macs on a Thunderbolt 5 cable work on the same token at the same time, exchanging 16-24 KB partial sums over RDMA or dedicated TCP sockets - cutting per-token latency, not just adding capacity.

DSpark speculative decoding

An experimental 5.6 GiB draft model proposes up to five future tokens; the main model verifies them in one pass. Predictable continuations - especially code - benefit most. Explicitly opt-in.

Power steering

--power 50 targets a GPU usage level by injecting micro-sleeps between prefill layers and decoded tokens - taming heat, fan noise, and battery drain without changing output math.

Single best feature

The KV cache that survives restarts

Standard APIs are stateless: switch sessions or restart the server and a 25,000-token system prompt gets re-prefilled from scratch, every time. DwarfStar's disk KV cache makes the saved prefix the resume mechanism - point Claude Code at it with --kv-disk-dir and later continuations reuse the expensive prefill instead of paying for it again.

The problem it solves

antirez calls it the generality trap: tools that try to run every model end up running the big ones badly.

Before
  • Traditional local runners (standard GGUF tooling) support every model under the sun - at the cost of generalized, bloated codepaths and unnecessary software layers.
  • On resource-constrained consumer hardware, that generality translates into massive performance degradation for 284B-class MoE models.
  • Stateless APIs discard context on every session switch or server restart, forcing expensive re-prefills of 25,000+ token system prompts on startup.
After
  • One unified, lightweight codebase: model loading, prompt rendering, tool calling, KV management, HTTP server, and a native coding agent, all in-process with zero socket overhead.
  • The disk is a first-class memory tier: aggressive expert-only quantization, SSD streaming, and persistent disk KV caching put 284B-parameter models on 128 GB laptops and 512 GB workstations.
  • Sessions survive restarts - the cached prefix on disk is loaded instantly instead of recomputed.

The bet is extreme model specialization: support exactly the GGUFs the author publishes, tune every codepath for them, and let everything else fail loudly rather than run slowly.

Setup

Native backends for Metal (macOS), NVIDIA CUDA (Linux), and ROCm on Strix Halo APUs. Three steps: clone, build, download.

01

Clone and build for your backend

git clone https://github.com/antirez/ds4 && cd ds4
make               # macOS (Metal)
make cuda-spark    # Linux CUDA - DGX Spark / GB10
make cuda-generic  # Linux CUDA - generic GPUs (or: make cuda CUDA_ARCH=native)
make strix-halo    # Linux ROCm - AMD Strix Halo
make cpu           # CPU-only diagnostics

If compilation fails on a clean VM, install gcc first - the build errors point straight at the missing compiler.

02

Download the specialized GGUF

The script auto-resumes interrupted downloads and saves under ./gguf/. Pick by RAM:

./download_model.sh ds4f-q2      # 96/128 GB machines - 2-bit Flash GGUF
./download_model.sh ds4f-q4      # 256 GB+ machines - 4-bit Flash GGUF
./download_model.sh ds4f-dspark  # optional DSpark draft model, ~5.6 GiB
03

Run it

./ds4                                          # interactive CLI, thinking on by default
./ds4 --nothink -p "List three Redis design principles."

Or serve it to any OpenAI/Anthropic-speaking client (Claude Code, coding agents) with disk KV caching on:

./ds4-server --ctx 100000 --kv-disk-dir /tmp/ds4-kv --kv-disk-space-mb 8192

Real-world numbers

Built first for Apple Silicon, and the benchmark table shows it - unified memory bandwidth is the star of this show.

At 2048 context. Stretch the context to 65,536 tokens and it still holds 27.64 t/s generation with 398.50 t/s prefill - a laptop running a frontier-class MoE at usable interactive speed.

NVIDIA DGX Spark GB10, 128 GB, CUDA, 2-bit quant

At 2048 context. Prefill edges out the Mac, but generation lands at roughly half - CUDA bandwidth on that machine is simply different from Apple unified memory.

Mac Studio M3 Ultra, 512 GB, Metal

2-bit quant with 468.03 t/s prefill. The same machine running the bigger PRO 2-bit model via SSD streaming still produces 9.56 t/s on 32,768-token prompts.

120 t/saggregate · 2000 t/s prefill

8x NVIDIA L40S enterprise server, micro-batched serving

Aggregated generation across multiple concurrent sessions - the same engine scaling from a laptop to a serving box.

3.5x~4.8 → ~16.8 t/s decode

Two MacBook M5 Max over Thunderbolt 5 RDMA, GLM 5.2

Tensor parallelism splits the expert load 50/50; decode jumps from a sluggish ~4.8 t/s (single machine, SSD streaming) to ~16.8 t/s with ~94 t/s prefill. Startup takes about 9 seconds per machine as each rank pre-faults its ~100 GiB shard and pins it through a Metal residency set.

Watchouts

DwarfStar is bleeding-edge by design. The author flags most of these himself - read them before you download 81 GB of weights.

BETA QUALITY, MOVING FAST

The codebase is rapidly changing and instabilities are common. The distributed protocol has no native encryption or authentication - trusted local networks only.

NOT A GENERAL GGUF RUNNER

Pointing it at an arbitrary Hugging Face GGUF will fail to load. Tensor layout, quantization mix, metadata, and MTP state must exactly match the specialized GGUFs published by the author. Other quant layouts are unsupported until deliberately added and scored against the official 100-case fixture.

APPLE SILICON GETS THE LOVE

Built first and foremost for macOS/Metal. CUDA and ROCm are supported, but NVIDIA and AMD paths occasionally fall back to slower exact execution layers when native batched kernels are unavailable. If something behaves differently on your Linux GPU, that is why.

AN 80 GB H100 IS NOT ENOUGH

A single H100 with 80 GB of VRAM fails immediately with an out-of-memory crash. The model files demand a strict minimum of 96 to 128 GB of addressable memory just to load - before CUDA runtime overhead even touches it.

SSD STREAMING CAN CRAWL

Running larger-than-RAM models over SSD streaming on lower-end devices can drop below 1 t/s - or 0.1 t/s on external USB drives. That mode suits offline batch runs, not active chat.

AI-BUILT, OPENLY DISCLOSED

The README notes the software was developed with strong assistance from GPT 5.5, 5.6, and Claude Fable, and the author is blunt about it: "If you are not happy with AI-developed code, this software is not for you."
