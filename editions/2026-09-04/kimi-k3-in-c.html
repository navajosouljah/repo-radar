● What makes it different

MoE sparsity exploit

Kimi K3 has 896 experts per layer but only 16 fire per token. 93% of the 1.447 TB checkpoint - the routed experts - never enters RAM. They stream from NVMe on demand.

Zero dependencies

No BLAS, no framework, no GPU driver. The only requirements are libm and OpenMP. Compiles with any C99-compliant compiler on any POSIX system.

LRU expert cache

An in-memory LRU cache of recently used experts handles cache hits from resident memory. Misses read from NVMe via O_DIRECT, bypassing the OS page cache entirely.

MXFP4 native quantization

Uses SiTU-GLU and native MXFP4 expert weights from the Kimi K3 checkpoint. No additional quantization step - the model ships in this format.

Seven source files

The entire engine is 176 KB of C across seven source files. Every line is readable, debuggable, and modifiable - built as a teaching artifact.

Full 93-layer architecture

Runs the complete model - 69 KDA layers, 24 Gated MLA layers, top-16 expert selection. No shortcuts, no layer pruning, no accuracy tradeoffs.

Single Best Feature

The memory wall was a loading problem, not a model problem

Everyone assumed running 2.78 trillion parameters required a GPU cluster. This project proves the constraint was never the model itself - it was how we loaded it. By streaming only the 16 active experts per layer from disk and keeping everything else on NVMe, the peak memory footprint drops from 1.56 TB to 8.24 GB. The output is byte-identical to the full-memory version.

The memory wall

Trillion-parameter models were supposed to require a rack of H100s. The memory limit everyone took for granted was a property of how we load models, not the models themselves.

Before

GPU cluster required. Running Kimi K3 at full precision meant distributing 1.56 TB of weights across 32 H100 GPUs. That is roughly $1M in hardware, accessible to a handful of labs.

Opaque inference stacks. Inference runs through PyTorch or vLLM with layers of abstraction. When something goes wrong at layer 47, good luck debugging it on a machine you do not own.

No personal debugging. If you deploy K3 on 32 GPUs at work and hit a problem, you cannot reproduce it at home. The model does not fit in any consumer hardware configuration.

After

One CPU, 8 GB RAM. Stream experts from a fast NVMe drive. Only the 16 active experts per layer reside in memory at any point. The rest stay on disk.

176 KB you can read. Seven C files, no frameworks. Every matrix multiply, every router decision, every cache eviction is visible and debuggable with gdb.

Debug at home. The same model, the same weights, the same outputs - running on a workstation you own. Reproduce production bugs on personal hardware.

Get running

Clone, compile, download the checkpoint, and run inference. Requires a C99 compiler, a fast NVMe drive with 1.6 TB free, and 8+ GB of RAM.

1

Clone the repository

# Clone kimi-k3-in-c
git clone https://github.com/FareedKhan-dev/kimi-k3-in-c.git
cd kimi-k3-in-c

The repo is small - 176 KB of source across seven files in src/.

2

Build the binary

# Build with make (any C99 compiler works)
make

# Or compile directly with gcc
gcc -std=c99 -O2 -fopenmp -o kimi-k3 src/*.c -lm

No BLAS libraries, no CUDA toolkit, no Python. Just a C compiler and libm.

3

Download the Kimi K3 checkpoint

# Download the MXFP4 checkpoint (~1.56 TB)
# Follow the instructions in docs/ for your
# preferred mirror (HuggingFace, ModelScope)
python scripts/download_checkpoint.py \
  --model kimi-k3 \
  --format mxfp4 \
  --output ./checkpoint/

You need a fast NVMe drive with at least 1.6 TB free. Sequential read speed directly affects tokens-per-second on cache misses.

4

Run inference

# Run with default settings
./kimi-k3 --checkpoint ./checkpoint/ \
  --prompt "Explain the Riemann hypothesis"

# Tune expert cache size (default fits in 8 GB)
./kimi-k3 --checkpoint ./checkpoint/ \
  --cache-size 64 \
  --prompt "Write a Python web server"

The --cache-size flag controls how many experts stay resident. Larger values use more RAM but reduce NVMe reads on repeated expert activations.

Real-world use

How engineers and researchers are using kimi-k3-in-c to study, debug, and deploy trillion-parameter inference without GPU infrastructure.

Debug at home

Reproduce production bugs on personal hardware. The author built this after deploying Kimi K3 on 32 H100 GPUs at work and being unable to debug on personal hardware. With this engine, any developer can step through inference with gdb on a single machine.

Teaching tool

Understand MoE architecture hands-on. Seven readable C files with no framework abstractions. Students and researchers can trace exactly how a 2.78T-parameter MoE model routes tokens, activates experts, and produces output.

Edge inference

Run frontier-class models without GPUs. Any machine with a fast NVMe drive and 8 GB of RAM can run inference. Useful for air-gapped environments, embedded systems with NVMe storage, or cost-sensitive deployments.

Architecture research

Experiment with expert routing and caching. The LRU cache and O_DIRECT NVMe streaming are modifiable. Researchers can test alternative routing strategies, cache policies, and quantization schemes without touching a GPU cluster.

Watch out for

  • NVMe speed is the bottleneck. Tokens-per-second on cache misses depends entirely on your drive's sequential read speed. A slow SATA SSD will make inference painfully slow. Budget for a fast Gen4 or Gen5 NVMe.
  • 1.56 TB checkpoint download. You need the full Kimi K3 MXFP4 checkpoint on a local drive. That is a serious download and storage commitment before you can generate a single token.
  • Slow compared to GPU inference. This is a teaching and debugging tool, not a production serving engine. Expect seconds per token, not milliseconds. The value is accessibility and debuggability, not throughput.
  • Young project - one month old. Created August 1, 2026, with active development. Expect breaking changes, incomplete documentation, and rough edges. The roadmap in docs/ROADMAP.md outlines planned improvements.
