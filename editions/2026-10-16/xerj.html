How does it work?

Your problem

AI agents that need to search your files read them one by one into their conversation, using up working memory fast. Or they use basic text-matching (like a find-in-files command) and miss what they need.

Your agent needs to find how a function is used across a codebase. It reads file after file, burning through its memory budget, and still misses the relevant one.

When it kicks in

You run one command - xerj autoindex ~/my-project - and the engine indexes the folder in the background. Then agents search the index instead of reading files.

Index a project folder once. The engine detects file types automatically - code, JSON, CSV, PDF, email - and creates the right indexes for each.

You give it

A folder of code, documents, logs, or data files. Supports 13 format families: source code in 36 languages, PDF, spreadsheets, JSON, CSV, email, and more.

A checkout of a large open-source project, a folder of PDF research papers, or a directory of server logs.

It does

It indexes your files and serves search results through a standard interface that AI agents and existing tools already understand.

  1. Detects each file's type automatically and indexes its contents - source code is parsed by structure (using tree-sitter), so function names and definitions are preserved
  2. Offers keyword search, meaning-based search, and a hybrid of both, all from a single search command
  3. Speaks the Elasticsearch query language, so any existing tool, dashboard, or script that queries Elasticsearch works without changes

Index an 80-file codebase. The agent searches for 'database connection retry logic' and gets the right file on the first try - versus scrolling through files one by one.

You get

AI agents that search faster, use less memory, and find the right files without reading everything.

  • Faster, more accurate searchAn AI agent finds the right file on its first search 94% of the time, versus 38% with basic text search
  • Less memory usedAgents that search the index use 2.7 times fewer output words than agents that read files with find-in-files commands
  • Agent memoryA built-in memory store lets agents save and recall facts between sessions, with per-agent isolation

What changes for me?

Without it

  • AI agents that need to search your files read them one by one, filling their working memory and slowing down. A 500-file codebase means hundreds of file reads.
  • Basic text-matching finds exact strings but misses meaning. Searching for 'retry logic' won't find a function called exponential_backoff unless the comment mentions 'retry'.

With it

  • One command indexes the folder. AI agents search the index and get structured results - function definitions, line numbers, and context - without reading every file.
  • Hybrid search combines keyword matching and meaning, so 'retry logic' finds exponential_backoff even without an exact match. The right file comes up first 94% of the time.

How hard is it to try?

Effort

5 minutesAbout an hourNeeds a developer
  1. Install with one command: curl -fsSL https://xerj.org/get | sh (Mac/Linux) or irm https://xerj.org/get.ps1 | iex (Windows).
  2. Start the engine and index a folder: xerj --insecure --data-dir ./data & then xerj autoindex ~/some-project.
  3. Try a search: curl 'http://localhost:9200/your-index/_search?q=your+query' or try the live playground.

What it takes on your computer

Space on disk
Ships as a single static binary - no Java, no dependencies. Download size not published. The optional neural search mode downloads about 90 MB of model files.
Memory while it runs
No data found. Default search mode is lexical (no neural models loaded). Neural mode loads three model files locally.
Runs on
Mac, Windows, and Linux on x86-64 and arm64. Linux builds are statically linked, so they run on any distribution including Alpine. Built from source with a stable Rust toolchain.

Should I?

Great if you...

  • You work with AI agents that search codebases, document folders, or log archives - Xerj replaces file-by-file reading with indexed search
  • You want a lightweight local search engine with no Java dependency that speaks the Elasticsearch language - existing tools and dashboards just work

Skip it if...

  • You need a production Elasticsearch replacement with full feature coverage - 3 of 1,369 conformance tests fail, and features like scroll cursors behave differently
  • You want neural (meaning-based) search out of the box - the default mode is keyword-only, and neural mode requires downloading model files and is still opt-in
  • You need a battle-tested tool - this is 108 days old with no named production users

Instead, you could look at

  • ElasticsearchThe industry standard. Full-featured and production-hardened, but requires Java, more memory, and more setup. Xerj is designed as a lighter local alternative.
  • ripgrepA fast text search tool. No indexing, no server - just searches files directly. Faster for one-off searches, but does not offer meaning-based search or an agent-friendly interface.
  • MeilisearchAn instant-search engine in a single binary. Focused on user-facing search with typo tolerance. Does not parse source code by structure.

Is it safe?

PASSED
  • Security advisories: 0GitHub's advisory list, checked Oct 16
  • Searches for CVEs, vulnerabilities, malware and scams12 results read, including the national CVE database: nothing found
  • Are the stars earned?6.4K stars, 37 contributors, 3.1K commits. No findarepo data found.

Watch out for

  • Young project - 108 days old with no named production users. The benchmarks are the project's own and have not been independently reproduced. The claim of '40x fewer tokens than grep' in the About section contradicts the body's '2.7x' figure.
  • Default mode listens without authentication. The --insecure flag disables all authentication and encryption. Anyone on the network can query, index, and delete data. Authentication is on by default without that flag, but the quickstart guide uses it.
  • Optional reranking sends data to an external service. The Jev reranker (by TypeSafe AI) sends search result text to an external API for re-scoring. It is off by default, but you should know it exists before enabling it.
  • Not a drop-in Elasticsearch replacement. Three conformance tests fail, scroll cursors are bounded snapshots (not infinite streams), and some aggregation features are missing. The project calls itself a 'migration bridge, not a clone.'
