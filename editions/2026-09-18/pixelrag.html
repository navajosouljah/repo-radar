● What makes it different

Pixel-native retrieval

Instead of converting documents to text, PixelRAG renders them as images and uses vision-language models to embed and search the visual representation. Tables, charts, code blocks, and mixed layouts are captured exactly as displayed.

No parsing pipeline

Traditional RAG systems need parsers for every document type - PDF extractors, HTML cleaners, table detectors. PixelRAG eliminates the entire parsing layer. If it renders in a browser or viewer, it is searchable.

Research-backed architecture

The system is based on arXiv paper 2606.28344, which demonstrates that pixel-native retrieval matches or exceeds text-based RAG on standard benchmarks while handling visual content that text pipelines miss entirely.

Scalable chunking via screenshots

Pages and documents are chunked as visual tiles - scrolling screenshots of fixed viewport size. Each tile is embedded by a vision model, creating a searchable index of visual content without any text extraction step.

Works with messy real-world content

Scanned PDFs, image-heavy slides, dashboards with charts, pages with complex CSS layouts - content that breaks every parser works out of the box because PixelRAG never tries to extract structure. It just looks at what is rendered.

Multimodal search queries

Search queries can be text or images. Ask PixelRAG to find pages that look like a given screenshot, or search by description. The vision embedding space handles both modalities natively.

Single best feature

Parse nothing, search everything

The insight behind PixelRAG is that parsing is a lossy, brittle step that every RAG pipeline struggles with. Tables get mangled, charts become gibberish, CSS layouts lose their meaning. By operating on pixels instead of text, PixelRAG sidesteps every parsing failure mode at once. The tradeoff is compute - vision models cost more per token than text embeddings - but the accuracy gains on visual content are dramatic, and the engineering simplicity of "just screenshot it" is hard to overstate.

The parsing problem

Every RAG system today relies on extracting text from documents. That extraction step is where quality goes to die.

Before

Parsing is the bottleneck. PDF extraction misses tables. HTML cleaners destroy layout. Markdown converters hallucinate structure. Every document type needs its own parser, and every parser has failure modes.

Visual content is invisible. Charts, diagrams, screenshots, and infographics contain critical information that text extraction cannot capture. A bar chart becomes a list of numbers - if you are lucky. Usually it becomes nothing.

Layout carries meaning. A two-column comparison, a sidebar with caveats, a footnote that qualifies the main text - spatial relationships that humans read instantly are lost when content is flattened to a text stream.

After

No parsing, no loss. PixelRAG screenshots the rendered page. Whatever a human would see is exactly what gets indexed. Tables stay tables, charts stay charts, layouts stay layouts.

Universal document support. If it renders in a browser or viewer, it is searchable. No per-format parsers to maintain, no extraction heuristics to tune. One pipeline handles every document type.

Spatial understanding preserved. Vision-language models understand spatial relationships natively. A comparison table, a sidebar callout, a header-grouped section - the visual structure is part of the embedding.

Get started

From zero to a working setup in minutes.

1

Clone and install

git clone https://github.com/StarTrail-org/PixelRAG.git
cd PixelRAG
pip install -e .

The repository includes the core library, indexing pipeline, and a demo search interface. Python 3.10+ required. A vision-language model (local or API) is needed for embedding.

2

Index your documents

# Index a directory of PDFs, web pages, or any renderable files
pixelrag index ./documents --viewport 1280x720

# The indexer renders each page as a screenshot,
# chunks it into tiles, and embeds each tile
# using your configured vision model.

The indexing step renders each document, tiles the screenshots, and creates vision embeddings. GPU recommended for local models; API-based models work but cost per-image.

3

Search your index

# Text search
pixelrag search "quarterly revenue breakdown by region"

# The system returns matching visual tiles
# with highlighted regions and source documents

Search returns the visual tiles that match your query, along with source document references and confidence scores. Results include the rendered visual context, not extracted text.

Real-world scenarios

Where this project earns its place in your stack.

Financial Document Search

Find data in complex financial reports. Annual reports, earnings presentations, and regulatory filings are full of tables, charts, and multi-column layouts that text extraction mangles. PixelRAG indexes them as rendered pages, so searching for "Q3 revenue by segment" returns the actual chart or table, correctly formatted, from the right slide.

Enterprise Knowledge Bases

Search across mixed-format internal docs. Confluence pages with embedded diagrams, Google Slides decks, PDF specifications with technical drawings - enterprise knowledge lives in visual formats. PixelRAG handles them all without format-specific parsers.

Research Paper Analysis

Find figures, tables, and equations across papers. Academic papers are dense with visual content that text extraction destroys. PixelRAG can find the figure that shows a specific architecture, the table comparing benchmark results, or the equation defining a loss function.

Web Content Archival

Index and search web pages as they appeared. Web pages are designed for visual consumption. Instead of stripping HTML to text and losing the design, PixelRAG captures the rendered page and makes it searchable with full visual context.

In the Wild

  • Peer-reviewed research. PixelRAG is backed by arXiv paper 2606.28344, establishing its theoretical foundation and benchmark results against traditional text-based RAG systems.
  • Rapid community adoption. Nearly 10K stars and 857 forks in under four months signal strong developer interest in the pixel-native approach. The repo's topics - agent, AI, memory, multimodal, RAG, search, vision - show its positioning at the intersection of multiple hot areas.
  • Vision-language model momentum. PixelRAG rides the wave of increasingly capable VLMs. As models like GPT-4V, Claude's vision, and open-source alternatives improve, the pixel-native approach becomes more practical and accurate.
  • Coverage is research-focused. Most discussion centers on the paper and methodology rather than production deployments. Real-world case studies at scale are emerging but not yet widely published.

Watch out for

  • Compute cost. Vision embeddings are significantly more expensive than text embeddings. Indexing a large document corpus requires substantial GPU time or API spend. The pixel-native approach trades engineering complexity for compute cost.
  • Latency at query time. Vision model inference is slower than text embedding lookup. For real-time search applications, expect higher latency than traditional vector search. Caching and pre-computation help but do not eliminate the gap.
  • Viewport dependency. Results depend on how documents render at the chosen viewport size. A responsive web page looks different at 1280px vs 768px. Mobile-optimized content may need separate indexing passes.
  • No text-level granularity. PixelRAG returns visual tiles, not specific text spans. If you need to extract and manipulate the text content of results, you still need OCR or a text extraction step downstream.
