Memory that persists across sessions

ai-memory is an MCP server that gives coding agents persistent, searchable memory. Store project decisions, coding patterns, architecture notes, and contextual knowledge that your agent can recall across sessions. No more re-explaining your codebase every time you start a new conversation.

● What makes it different

Persistent memory store

Memories persist across agent sessions in a local SQLite database with vector embeddings. Project decisions, architecture patterns, coding conventions, and context survive session boundaries.

Semantic search retrieval

When your agent needs context, it searches by meaning, not keywords. Ask about authentication patterns and it retrieves memories about auth architecture, session handling, and security decisions even if they do not contain the word "authentication."

MCP protocol native

Runs as an MCP (Model Context Protocol) server, the emerging standard for agent tool integration. Works with Claude Code, Codex, and any MCP-compatible harness without adapter code.

Structured memory types

Memories are categorized: decisions, patterns, conventions, context, and notes. Each type has metadata for priority, scope, and relevance. The agent can store and retrieve with type-specific queries.

Project-scoped isolation

Memories are scoped to projects. Your React project's conventions do not leak into your Go project's context. Each project gets its own memory namespace with independent search.

Automatic context injection

Configure memory categories to auto-inject into agent context at session start. Critical decisions and conventions are always present without the agent needing to search for them.

Single best feature

Your agent remembers what you decided and why

The most valuable use of ai-memory is storing decisions with their rationale. "We chose Postgres over MongoDB because of the relational nature of our data model and the need for transactional consistency across user and order tables." Three months later, when a new developer (or a new agent session) asks why you use Postgres, the memory is there with the full reasoning. This is the kind of institutional knowledge that normally lives in someone's head and disappears when they leave. ai-memory makes it persistent and searchable.

The agent amnesia problem

Every coding agent session starts from zero. Your agent does not remember what it learned about your codebase yesterday, last week, or last sprint.

Before

Every session is a blank slate. You explain your project structure, coding conventions, and architecture decisions at the start of every agent session. The agent re-discovers the same patterns, asks the same questions, and makes the same mistakes.

Context files are static. CLAUDE.md and similar context files help but they are manually maintained text dumps. They do not support semantic search, have no priority or categorization, and grow unwieldy as projects mature.

Tribal knowledge disappears. Decisions made in conversation - why you chose this database, why that endpoint is structured this way, why this pattern exists - vanish when the session ends. The next session has to reconstruct the reasoning.

After

Persistent project memory. Decisions, patterns, and conventions are stored and survive across sessions. The agent starts each session with access to everything it has learned about your project.

Semantic retrieval. The agent searches by meaning, not string matching. "How do we handle authentication?" retrieves all relevant memories about auth architecture, token handling, and session management.

Structured and searchable. Memories are categorized and prioritized. Critical architecture decisions surface automatically; implementation details are available when searched. The agent gets the right context at the right time.

Set up ai-memory

Add persistent memory to your coding agent in under five minutes. No external services required.

1

Install the MCP server

npm install -g @akitaonrails/ai-memory

# Or run directly with npx
npx @akitaonrails/ai-memory serve

ai-memory runs as a local MCP server. It uses SQLite for storage and local embeddings for semantic search. No cloud services, no API keys for the memory layer itself.

2

Configure your agent

# Add to your Claude Code MCP config (.claude/mcp.json)
{
  "mcpServers": {
    "ai-memory": {
      "command": "npx",
      "args": ["-y", "@akitaonrails/ai-memory", "serve"]
    }
  }
}

Once configured, your agent has access to store and retrieve memory tools. It can save decisions, patterns, and context during any session.

3

Store and recall memories

# In your agent session, memories are stored naturally:
# "Remember that we use Postgres for the user service
#  because of transactional consistency requirements."

# Later, in any session:
# "What database do we use for the user service and why?"
# -> Agent retrieves the stored memory with full context

Memories are stored with semantic embeddings for meaning-based retrieval. The agent can search, update, and delete memories as project context evolves.

Where ai-memory fits

Any workflow where agent continuity across sessions matters benefits from persistent memory.

Architecture Decisions

Record the "why" behind every decision. Store architecture decision records - database choices, framework selections, API design patterns - with their rationale. Future sessions retrieve the reasoning instantly, without reading through old PRs or Slack threads.

Coding Conventions

Conventions that stick. Store your project's coding style, naming patterns, error handling approach, and testing strategy. The agent follows your conventions from the first line of every session, not just after you remind it.

Onboarding Context

New team members get agent-assisted onboarding. The project's memory contains institutional knowledge - why things are the way they are, what was tried and rejected, where the gotchas hide. A new developer's agent has the same context as a tenured team member's.

Cross-Session Workflows

Multi-day tasks maintain continuity. Start a refactoring on Monday, continue on Wednesday, finish on Friday. The agent remembers what was done, what is left, and what decisions were made along the way.

Watch out for

  • Memory curation is your job. ai-memory stores what you tell it to. If you store low-quality or outdated information, the agent retrieves low-quality or outdated context. Periodic review and cleanup of stored memories is important.
  • Embedding model quality matters. Semantic search quality depends on the embedding model. The default local model works well for code-related queries but may miss nuances in business-domain terminology.
  • Not a knowledge base replacement. ai-memory is designed for agent context, not as a general-purpose knowledge management system. It stores memories, not documents. For comprehensive documentation, use a proper documentation system.
  • Storage grows with usage. The SQLite database grows as memories accumulate. Large projects with extensive memory usage should monitor disk usage and periodically archive or prune old memories.
