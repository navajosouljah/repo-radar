# Product

## Register

brand

## Users

JJ Gilmore: a non-coder executive who runs several businesses (healthcare sales operations,
investor newsletters, client brand builds) and is learning to work with Claude Code. He is a very
visual learner. He reads Repo Radar on Friday mornings at his desk in a bright office, and on his
phone between meetings. He skims about ten tools in fifteen minutes. The job is to decide, for each
repo, *try it / skip it / keep an eye on it*, and to understand the value without clicking out to
GitHub or the project's website.

Secondary readers are the people JJ shares a page with (his team, partners). They know even less
context than he does.

## Product Purpose

Repo Radar is a weekly radar of the open-source tools worth knowing: this week's Top 10, a
leaderboard per category, and a Claude Board of the most-installed Claude skills and plugins. Each
repo gets a one-page answer sheet, in this order (set by JJ, Sep 27 2026): what it is, with a real
picture and the key numbers; how it works; what changes for you; how hard it is to try and what it
takes on your computer; whether you should; whether it's safe; and last, who's using it and who's
talking about it.

The Top 10 is picked for tools a non-coder can install or use with Claude Code. Developer-only
launches are labeled and never crowd those out.

Success: JJ stops clicking out to GitHub to understand a repo, and trusts every pick to be both
popular and safe.

## Brand Personality

A sharp friend at a whiteboard: **clear, visual, candid.**

- Clear: plain English first, jargon only when explained.
- Visual: show the thing working before explaining it.
- Candid: say when evidence is thin, when a tool is for developers only, and when something is
  unsafe, in the first line, not buried.

The feeling to leave behind: "oh, I get it", and trust.

## Anti-references

- The previous Repo Radar pages: a dark "terminal" look, a different random skin on every page, four
  tabs hiding most of the content, spec-sheet stats, and code as the setup step.
- SaaS landing templates: a big-number hero, identical icon-heading-text card grids, gradient accents.
- GitHub READMEs: walls of text and install commands before any "why".
- Hype newsletters: "game-changer" language, uncited claims, star counts presented as proof.

## Design Principles

1. **Show, then tell.** A picture of the tool working, and a board of *you -> tool -> result*,
   before any paragraph.
2. **Plain English or it doesn't ship.** Every headline, board note and before/after passes the
   jargon test. A technical term is explained the first time it appears.
3. **Same place, same meaning.** Every repo page uses the same order, and the same colors mean the
   same thing everywhere: yellow is the problem, blue is how it works, green is what you get, coral
   is watch out. Skimming becomes pattern recognition.
4. **Every claim cited, every number real.** Sources are dated. Missing data says "no data found".
   Nothing is invented.
5. **Safety verdict up front.** The gate result is visible at the top of every page, and a failed
   repo gets a red DO NOT INSTALL page, never a normal one.

## Accessibility & Inclusion

- WCAG 2.2 AA.
- Color is never the only signal: the legend colors always come with a label or icon.
- Body text is at least 16px, readable on a phone, and works at 200% zoom.
- `prefers-reduced-motion` is respected.
- Link text makes sense on its own.
